Five ways a SaaS app is laid out

Layout only — no colour, no typography, no brand. Each pattern below places the same seven regions in a different arrangement, drawn at desktop and at 360px. The notes column prices each one against TalentTrack’s current frontend (132 stylesheets, 67 shared views, 92 module views, one central chrome renderer in DashboardShortcode).

ABrand / tenant — club identity, logo
BPrimary nav — every module the user can reach
CSecondary nav — section or record tabs
DContext header — breadcrumb, record identity, page actions
EContent — the work surface
FUtility — search, alerts, help, persona/user menu
GDetail / inspector — the selected record, in-place
▪Today — TalentTrack has A, D, E, F. No B, no C.
01

Sidebar shell

Seen in Stripe, Linear, Notion, Jira, Vercel, HubSpot

A full-height left rail carries every module, grouped. The content column owns its own context header. This is the default shape of the modern B2B web app, and the only one of the five that scales past ~30 destinations without hiding things.

Fit for TalentTrack

  • Nav model already exists. TileRegistry holds slug, group, order, icon, per-persona label and cap for every destination, and groupOrder() already fixes the group sequence (Performance / People / Planning & tactics / Development / Reference). A sidebar is a second renderer over that data — not a new information architecture.
  • One chrome chokepoint. The header is emitted in one place (DashboardShortcode, ~line 1510) inside a document TalentTrack already controls (CanvasShell + templates/canvas.php). The shell wrapper lands there, once.
  • Cost is the width contract. Content loses ~210px. Views using max-width / grid / minmax() reflow for free; the ~20 sheets using position:fixed, sticky or 100vw need review — the wide grids (ratings, minutes, attendance) and the match-execution sideline view are the real ones.
  • Collides with CLAUDE.md §5. Two nav affordances per view, no third. A persistent global rail is a third one unless §5 is amended to exempt app chrome. That is a decision, not a bug — but it must be made before code.

Effort

MEDIUMNew nav component + one stylesheet + shell wrapper + drawer JS, then a width audit across ~20 stylesheets. No routing change, no view rewrites.
02

Top nav (horizontal)

Seen in GitHub, Basecamp, Xero, Mailchimp, Google Analytics

A global bar carries brand + utility; a second band underneath carries the primary destinations as tabs. Content keeps the full viewport width. Cheap, familiar, and it stops scaling once the tab row overflows — which is its main limit, not a fatal one.

Fit for TalentTrack

  • Purely additive. Content width does not change, so no view and no stylesheet needs to be re-measured. That is the single biggest cost difference against pattern 1.
  • Same registry feed. Also reads TileRegistry, but the top row only fits ~8 destinations. TalentTrack has far more than 8 — so B becomes the five groupOrder() groups with a dropdown each, or an “More” overflow. That is a real IA decision: which five things are top-level.
  • C is where the win is. Record-level tabs (player: Overview / Journey / Evaluations / Goals / Minutes) directly answer the recurring “I can’t find X” feedback, and the player-profile surface is already flagged as the highest-leverage unmocked surface.
  • Mobile is the weak side. Two stacked scroll strips eat ~90px of a 640px viewport before any content. Pitch-side use argues for pairing this with pattern 5’s bottom bar on small screens.

Effort

SMALLOne nav band component + one stylesheet + an overflow rule. Everything below it stays as-is. The expensive part is the product decision about which destinations are top-level, not the code.

Three desktop panes collapse to a two-level stack: rail → bottom bar, panel → list screen, canvas → push navigation. C and E can never be on screen together.

Fit for TalentTrack

  • Needs a region split that does not exist. Today a list and its detail are two separate views at two separate URLs (?tt_view=players → ?tt_view=player&id=N), each rendering a whole page. Panel + canvas means one URL addressing two independently-rendered regions.
  • Routing and REST work. The panel has to load and re-filter without a full page render, so every list that becomes a panel needs its rows over REST. Per CLAUDE.md §4 those endpoints should exist anyway — but “should exist” and “exists” is exactly the gap docs/dev-tier-rest-port-backlog.md tracks.
  • Real payoff for one workflow. Evaluating a squad — 18 players, same form each time — is genuinely faster with a persistent roster panel. That is a narrow win for a whole-app restructure; a panel scoped to the evaluation surface alone would capture most of it.
  • Fights mobile-first. The pattern is inherently ≥1024px. CLAUDE.md §2 makes the 360px case the base case, and half the pilot use is pitch-side.

Effort

LARGEShell + routing model + REST panel loading + a pane-stack mobile fallback, then a per-surface port. Not one epic — a programme.

Fit for TalentTrack

  • Everything pattern 3 needs, plus an inspector. Same list/detail region split, same REST dependency, plus a fourth region with its own state.
  • Wrong primary shape for this product. A console optimises repetitive triage of interchangeable records. TalentTrack’s centre is one player’s longitudinal story (CLAUDE.md §1) — a surface that wants width and vertical room, not a 40%-width middle pane.

05

App shell + hub (bottom bar, tile launcher)

Seen in Strava, Duolingo, Monzo, Teamer, Spond, Google mobile apps

A slim top bar for identity, a centred content column, and a fixed bottom bar carrying the four or five things people actually do. Everything else lives behind a hub of tiles and a search field. Touch-native, thumb-reachable, and it hides the long tail by design — which is either the feature or the problem, depending on the user.

★

Sidebar + player spine + peek

Desktop 1 + record tabs from 2 + peek from 4 · Mobile 5

Richest and best-suited are not the same answer. The three- and four-pane workspaces (3, 4) feel the richest — but what makes them feel that way is not the pane count, it is that you never lose your place. That property is separable from the layout that usually carries it, and it can be bought without the pane cost.

So the recommendation takes the property and leaves the panes: a sidebar for global nav, a player context spine that pins the player's identity and their tabs across every surface inside that player, and a peek panel that opens a related record without navigating away from the one you are on. The spine is the part that is specific to this product rather than borrowed from a general-purpose SaaS shell — it is CLAUDE.md §1 made structural: the player is the root entity, so the player stays on screen.

Why this is the richest — and why the pane-heavy options are not

  • Richness is continuity, not density. What reads as premium in Linear or Superhuman is that context persists: you always know where you are and what you are looking at. Panes are one way to buy that. A pinned spine plus a peek panel buys the same thing at a fraction of the width cost.
  • The spine is this product's own idea. Every general SaaS shell has a sidebar. A header that pins the player — photo, name, team, position, age, status — across Overview / Journey / Evaluations / Goals / Minutes is specific to a talent system, and it is §1 expressed as layout rather than as a rule people have to remember.
  • Peek is what kills the dead ends. Today, following a link from a player to an activity means leaving the player. Peek keeps cross-entity moves reversible, which is the actual complaint behind most "I lost my place" feedback — and it composes with the existing RecordLink::detailUrlForWithBack() vocabulary rather than replacing it.
  • What the console would have bought, kept where it belongs. The queue treatment from pattern 4 still earns its place on the 3–4 genuinely queue-shaped surfaces (matches needing review, trial funnel, evaluation coverage). Adopt it there, not globally.

Why it is best suited

  • The primary surface wants width. A player's longitudinal story — timelines, rating trends, minutes over a season — needs horizontal and vertical room. A 40%-wide middle pane (4) or a 55% canvas (3) fights that; a sidebar plus full-width canvas does not.
  • Scales to the real destination count. There are far more than eight destinations, and the setup/report tail keeps growing. Only the grouped sidebar (1) absorbs that without hiding things behind "More".
  • Honours mobile-first properly. Mobile gets pattern 5 — bottom bar in the thumb zone, tile hub for the tail, compact sticky spine — which is what pitch-side use needs. Not a fallback of the desktop layout; the right layout for that viewport, fed by the same data.
  • Nothing here needs a rewrite. Sidebar and bottom bar both read TileRegistry. The spine is a component the record views call instead of their own hand-rolled headers. Peek is the one genuinely new mechanism.

Effort — phaseable, and the richness is the last phase

  • Phase 1 · S–M — persistent nav, both viewports. Sidebar ≥1024px + off-canvas drawer below + bottom bar on mobile, all from TileRegistry. Plus the width audit of ~20 stylesheets. This alone is most of the perceived change.
  • Phase 2 · S per surface — the spine. One component; adopted first by player detail, then team, activity, staff. Replaces per-view hand-rolled headers, so it removes code as it lands.
  • Phase 3 · M — peek + ⌘K. The one part needing new plumbing: REST reads for peeked records and a searchable index across players, teams, activities and views. Both are things §4 says should exist anyway.
  • Total ≈ Medium, spread over three releases, and each phase is shippable and useful on its own. Nothing in phases 1–2 is wasted if phase 3 is deferred.

The §5 amendment this needs

§5 currently counts all nav affordances. The fix is to distinguish global chrome from per-view affordances, and keep the ban where it was aimed — at hand-rolled per-view back links:

  • Global chrome — exactly one primary nav (sidebar ≥1024px / drawer + bottom bar below), rendered once by the shell from TileRegistry. Never emitted by a view.
  • Per view — still exactly two: the breadcrumb chain ending at Dashboard, and the contextual tt_back pill. Unchanged.
  • Record-scoped tabs are C, not a third affordance — they move within one record, they do not leave it. Rendered only by the spine component, never hand-rolled.
  • The original ban stands verbatim: no FrontendBackButton, no hardcoded "Back to dashboard" / "Back to <list>", no custom back affordance that sidesteps the chain + pill.

Three things that set the price, whichever pattern wins

1. The nav data already exists. TileRegistry carries slug, group, order, icon, per-persona label and capability for every destination, and groupOrder() fixes the group sequence. Any of these patterns is a new renderer over existing data — the information architecture is not the work.

2. The chrome has one chokepoint. DashboardShortcode emits the header in one place, and CanvasShell + templates/canvas.php already own the whole document and dequeue theme CSS. A shell wrapper goes in at one seam, not 159.

3. Content width is the only real risk. Patterns 1, 3 and 4 take horizontal room away from views. Most of the 132 stylesheets reflow, but ~20 use position:fixed, sticky or 100vw — the wide data grids and the match-execution sideline view are the ones to check first. Patterns 2 and 5 avoid this entirely.

Open decisions before any of this becomes an issue

CLAUDE.md §5 is being amended to separate global chrome (one primary nav, rendered once by the shell) from per-view affordances (still exactly two: breadcrumb chain + tt_back pill), with the original ban on hand-rolled back links kept verbatim. Proposed wording is on the ★ Recommended tab.

What is top-level? Patterns 2 and 5 force a choice of 5–8 primary destinations per persona — for the recommendation, that choice only constrains the five mobile bottom-bar slots, since the desktop sidebar carries the full grouped set.

Desktop and mobile are not the same pattern — settled. They share one registry feed and one set of destinations, and render as a grouped sidebar on a laptop and a thumb bar on a phone.
